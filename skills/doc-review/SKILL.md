# doc-review — SSOT 편집 (의미 보존)

**역할: 편집자.** 이 스킬 안에서 너는 문서를 읽기 쉽게 만드는 사람이지 정책을 정하는 사람이 아니다.
같은 규칙이 더 잘 읽히게 만드는 것까지가 네 권한이고, **규칙 자체가 바뀌는 순간 네 일이 아니다** —
그건 기획자(update-ssot)의 몫이다. 짧게 만드는 것이 목적이 아니라 **한 결정을 독립적으로 이해하고
검증할 수 있게** 만드는 것이 목적이다. 애매해서 못 줄이는 문장은 그대로 두고 보고한다.

## 공통 규칙 (모든 spec 스킬)
1. 먼저 spec/STATE.md를 읽는다. 없으면 중단하고 create-architecture 실행을 안내한다.
2. **문서 먼저**: 질문·추론·구현을 시작하기 전에 STATE.md에 시작을 기록하고(log 1줄 + 해당 st), 상태가 바뀔 때마다 즉시 반영한다. 병렬 세션은 STATE.md로만 서로를 안다.
3. 산출 문서는 spec/FORMAT.md 표기를 따른다. 규칙에 없는 표기는 만들지 않는다.
4. 질문·확인·보고는 cfg.lang 언어로, 상세도는 cfg.level대로. 산출 문서는 영어로 쓴다(FORMAT 언어 규칙). 선택지형 질문 도구(AskUserQuestion 등)가 있으면 사용.
5. **읽기**(FORMAT Reading): 한 번에 한 문서씩, 큰 문서는 섹션 단위로 읽는다. 마지막 섹션(ssot=`## chg`, task=`## result`)이 안 보이면 출력이 잘린 것이다 — 누락 범위를 다시 읽고 나서 판단한다. tasks/done/은 역사 기록이라 일괄로 읽지 않고, 특정 태스크·회귀 원인·이전 검증을 찾을 때만 연다.

## 1. 시작
- STATE 읽기 → 대상 확정: 사용자가 지정한 도메인(`doc-review THEME` 등), 없으면 ssot/ 전체를 rev·크기 순으로 훑어 **한 세션에 끝낼 수 있는 만큼만** 고른다(나머지는 next에 남긴다).
- 모드: 기본은 **정리**(편집까지 수행). 사용자가 "검토만/제안만"이라고 하면 제안만 하고 파일은 건드리지 않는다.
- log에 `- YYMMDD doc-review <IDs> start`.
- 신호 수집: `npx -y haeram-spec-creator lint`를 실행해 **검토 후보** 목록을 받는다(네트워크·CLI가 없으면 생략). 이건 출발점일 뿐이고, 후보가 아니어도 3단계 체크리스트에 걸리면 대상이다. 반대로 후보라고 해서 자동으로 고치지 않는다 — 판단은 이 스킬이 한다.
- 진행 중 작업 확인: STATE tasks의 doing 태스크가 참조하는 도메인은 결정 **분할을 하지 않는다**(인용줄 참조가 흔들린다). 문구 정리만 하고 분할 제안은 보고에 남긴다.

## 2. 대상은 ssot/만
편집 대상은 `spec/ssot/*.md`(ARCH 포함)뿐이다. **건드리지 않는 것**: 코드, `tasks/`·`tasks/done/`(역사 기록), `ideation/`·`review/`(자체 수명주기를 가진 작업 문서), STATE의 표(log·next만 갱신).

## 3. 점검 체크리스트 (결정 하나씩)
- **복합 결정** — 한 결정에 독립적으로 바뀔 수 있는 정책이 여러 개 들어갔나. 신호: ` ← ` 두 개 이상, ` · ` 세 덩어리 이상, 한 줄 700자 초과, "그리고 또"로 이어지는 나열.
- **과거 흔적** — 현재 동작과 무관한 요청 경위·승인자·날짜(`owner decision 2026-09-05`, `as discussed`, `user asked`), 과거 화면·과거 버그에 대한 해명, 폐기된 방식의 상세(수치 포함).
- **중복** — 같은 규칙이 여러 문서·여러 결정에 복사돼 한쪽만 고치면 어긋나는가.
- **명확성** — 주체(누가), 적용 범위(어디에), 조건(언제), 예외(단, ~일 때), 수치와 단위가 다 있는가. 빠졌으면 **채우지 말고** 보류 목록으로.
- **이력 간섭** — 폐기된 결정([x])과 변경 이력이 현재 규칙 읽기를 방해하는가. ([x]는 한 줄로, chg는 마지막 섹션에.)
- **복제** — 코드·다른 SSOT가 이미 정본인 상세를 옮겨 적었는가. → 정본을 가리키는 참조로.
- **읽기 완결성** — 문서를 읽다 출력이 잘리지 않았나. `## chg`까지 봤는지 확인하고, 못 본 범위를 판단 근거로 쓰지 않는다.

## 4. 편집 (의미를 보존하는 것만)
할 수 있는 것:
- **구조화** — 긴 한 줄을 결정 블록(FORMAT)으로 편다. 조건·예외·열거값을 2칸 들여쓴 하위 항목이나 표로 내린다. 값이 (조건, 값) 쌍으로 나열되면 표가 낫다.
- **분할** — 독립적으로 바뀔 수 있는 정책을 별도 결정으로 뗀다. **원래 번호는 머리 정책이 그대로 가져가고, 떨어져 나간 정책만 새 번호(현재 최대+1)를 받는다.** 번호 재사용·재번호 매기기 금지 — `→<ID>-n` 참조와 태스크 인용줄이 그대로 유효해야 한다.
- **통합** — 중복은 정본 한 곳에 남기고, 사본 쪽 결정은 **지우지 말고** 참조 한 줄로 바꾼다(`- PUB-7 [o] publish auth follows →AUTH-3`). 결정 ID는 절대 사라지지 않는다.
- **제거** — 요청 경위·승인자·날짜·과거 버그 서술·미사여구. 남는 것은 지금 지켜야 하는 규칙과 필요한 ← 이유뿐.
- **참조로 대체** — 코드나 다른 SSOT가 정본인 상세를 `→<ID>-n`이나 경로 한 줄로 줄인다.
- **골격 정리** — 골격 밖 섹션의 내용을 decisions로 흡수하거나 삭제, 섹션 순서 복원, chg 요약에서 서술 걷어내기(ID 표기와 `old→new`는 유지).

**대조 검증 (편집마다, 확인 요청 전에)** — 편집 전 원문에서 ① 조건 ② 예외 ③ 수치와 단위 ④ 부정 표현(no·never·only) ⑤ 의무 수준(must·should) ⑥ 참조(→)를 목록으로 뽑고, 편집 후 텍스트에서 하나씩 다시 찾는다. 하나라도 사라졌으면 편집을 되돌린다. 줄 수가 늘어도 괜찮다 — 줄이는 것이 목표가 아니다.

**rev·chg를 건드리지 않는다.** 문구 정리는 정책 변경이 아니므로 rev+1도, chg 줄도, STATE pending도 없다(FORMAT State rules). 그래서 정리만 했는데 태스크가 생기는 일이 없다.

## 5. 보류 — 편집으로 숨기지 않는다
다음은 **고치지 않고** 구체적으로 보고한다. 조건·수치·부정·의무·범위가 달라지면 그건 편집이 아니라 기획 변경이다.
- 서로 모순되는 두 결정 → 어느 쪽이 맞는지 정하는 건 사용자다. 두 원문을 나란히 제시.
- 조건·예외·수치가 빠진 공백 → "무엇이 빠졌는지"만 제시하고 추측으로 채우지 않는다.
- 뜻이 애매한 문장 → 해석해서 짧게 만들지 않는다. 원문 그대로 두고 물음만 남긴다.
- 현재 코드와 어긋나 보이는 결정 → 문서를 코드에 맞추지 않는다(코드가 틀렸을 수 있다).
- 이런 항목은 보고에서 `update-ssot <ID>` 한 건으로 묶어 next에 남긴다.

## 6. 반복 실행해도 흔들리지 않게
- 3단계 체크리스트에 걸리는 신호가 없는 결정은 **한 글자도 바꾸지 않는다.** 표현 취향으로 다시 쓰지 않는다.
- 이미 결정 블록으로 구조화된 결정을 다시 한 줄로 합치지 않는다 — 줄 합치기는 간결화가 아니다.
- 경고를 없애려고 기계적으로 쪼개지 않는다. 같이 바뀌어야 하는 정책은 한 결정으로 둔다.
- 같은 문서를 다시 돌렸을 때 바뀌는 게 없으면 정상이다. 보고에 "변경 없음"으로 적는다.

## 7. 마감
- **차이 확인**(git이 있으면 필수): 편집한 파일마다 `git diff -- spec/ssot/<ID>.md`를 읽고 ① 사라진 결정 ID가 없는지 ② 남은 결정의 `[o]`/`[x]`/`[?]` 표시가 그대로인지 ③ 삭제된 줄의 수치·부정 표현·참조가 편집본 어딘가에 남았는지 확인한다. 하나라도 어긋나면 편집이 아니라 정책 변경을 한 것이다 — 되돌리고 update-ssot로 넘긴다.
- 정리한 도메인마다 `npx -y haeram-spec-creator lint`를 다시 실행해 오류 0을 확인한다(결정 번호 중복, 골격, 참조 무결성).
- STATE: log 1줄(`- YYMMDD doc-review <IDs> tidied (rev unchanged)`), 보류 항목이 있으면 next에 `update-ssot <ID>` 1줄. ssot 표(rev·tasked·pending·[?])는 그대로 둔다 — [?] 수가 달라졌다면 편집이 아니라 정책 변경을 한 것이니 되돌린다.
- 보고(cfg.level대로, 별도 보고서 파일 없음): ① 정리한 것 — 도메인별 한 줄(무엇을 구조화·분할·통합·삭제했는지, 분할이 있었으면 `THEME-29 → THEME-29 + THEME-58..60`처럼 새 번호) ② 판단 보류 — 모순·공백·애매한 문장을 원문 인용 한 줄씩과 함께 ③ 다음 단계(`update-ssot <ID>` 또는 남은 도메인).
