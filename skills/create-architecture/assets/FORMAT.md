# FORMAT
> Notation rules for every doc under spec/. Write and read by these rules only. Never invent notation not defined here — define it here first, then use it.

## Principles
1. Primary reader is AI. No background prose, no fillers, no repetition. Decisions and reasons only.
2. One decision = one policy unit: a rule that can be read, applied and verified on its own. Split when two policies can change independently; keep together what must change together. Structure conditions as sub-lines or a table — never by joining them into one longer line. Removing line breaks is not concision.
3. Short ≠ omitted. Always keep: compatibility rules, failure conditions, security·billing·data-retention rules, numbers with their units, negations (no·never·only·must not), and the reason behind a non-obvious decision. Cut only what does not constrain the current implementation.
4. Docs first. Record state changes before reasoning or implementing: standalone/planning → STATE.md; a bound work-group worker → the work CLI runtime. Workers never edit STATE or SSOT.
5. Truth order: current rules → each SSOT's decisions·flow·constraints, progress → STATE.md for standalone or the work board for a work group, change history → each SSOT's chg (STATE log is a hint, not truth), past work → tasks/done/ (history, never a current rule). Fix mismatches in the owning workspace.
6. ssot/ holds outcomes only. Out: request traces ("user asked", "as discussed", who approved when), interview history, discarded alternatives beyond their one [x] line, past-bug narration, praise and filler, detail already owned by code or by another doc (reference it instead). In: the rule in force now, its conditions and exceptions, and the reason wherever a trade-off was made. Task files are disposable and may carry request context — ssot/ never does.
7. Scope exclusion ≠ rejected decision. A boundary that still holds ("free plan cannot export") is a live [o] decision written negatively. [x] means the decision is not in force any more.
8. A session runs in pair (the user is there to decide) or autopilot (nobody answers). Autopilot never waits for input: it takes the recommended option, writes it as an ordinary decision, and lists it in STATE inbox and the session report for the owner to confirm. ssot/ never records that a decision was provisional.

## Notation
- decision line: `- <ID>-<n> [o|?|x] <content>` + ` ← <reason>` only when there was a trade-off
  e.g. `- AUTH-2 [o] session: JWT 15m + refresh 30d ← minimize mobile re-login`
- decision block = the decision line plus the indented (2 spaces) sub-lines under it — sub-bullets or a table — carrying conditions, exceptions, enumerated values. Sub-lines have no ID of their own: the block is one decision, revised and referenced as one. Use them when the conditions do not fit one readable line; two reasons (` ← ` twice) or three or more ` · ` groups mean two decisions, not one long one.
  e.g. `- AUTH-4 [o] rate limit per account ← abuse without blocking shared offices`
       `  - login 5/min, password reset 3/hour`
       `  - over limit ⇒ 429 + retry-after, never a silent drop`
- [o] decided / [?] open / [x] rejected·not in force
- change kind: + added / ✎ modified / - removed (e.g. `AUTH-2✎`)
- reference to a decision: `→!AUTH-3` requires (this rule cannot be applied without it) · `→=AUTH-3` canonical (the target owns the rule this line points to) · `→~AUTH-3` related (background, looked up on demand) · `→AUTH-3` unclassified. One marker covers a `/` list or a `–` range (`→!AUTH-3/5`, `→AUTH-3–6`); `→AUTH` is a whole domain; a bare `AUTH-3` counts as unclassified.
  - write the kind when you write or revise the decision; never reclassify old references in bulk by guessing
  - a brief pulls requires and canonical targets transitively, follows unclassified ones one hop from a cited or required decision and lists the rest, and lists related ones without their text
- finding line: `- Fn [?|o|x] P1|P2|P3 <where>: <what>` + ` ← <why it matters>`; append ` →T###` once a task exists. P1 = correctness/security risk or blocks every change · P2 = slows every change · P3 = nice to have. A functional bug is a finding whose <what> starts with `bug:`
- acceptance check: `- [ ]` open → `- [v]` done (never mark done with x — [x] means rejected in SSOT)
- exploratory task: quote field `explore:<N>m|<N>h` is the timebox for work decided by running and measuring (calibrate·tune·balance). Its acceptance carries `- [ ] exit: <what gets recorded and why the task then counts as done when the timebox runs out>`
- inbox line: `- YYMMDD decided|parked|suggest <refs>: <text>` — refs are space-separated decision IDs (AUTH-3), task IDs (T012), `review/<slug>`, `ideation/<slug>` or `-`. decided = autopilot took an option: `<question> → <choice> (alt: <a> | <b>)` · parked = work left for the user and what it needs · suggest = an optional next step
  e.g. `- 261013 decided ECON-29 T062: bands unmet at the timebox → recorded the measured values (alt: widen the bands | change the rule)`
- time of day (STATE active·work): ISO 8601 UTC, `2026-10-13T07:44Z`
- rev: rN. +1 per policy change, one chg line (`- rN YYMMDD <ID>-n✎ summary`). First write: `- r1 YYMMDD initial`. A ✎ summary MUST keep the old value as `old→new` (e.g. `BM-11✎ limit 100→50`); a `-` summary states what was removed. Wording-only editing (doc-review) is not a policy change: no rev, no chg line.
- chg lines are never deleted or folded away — an unconsumed delta and an in-flight task's freshness check both read them. A summary may be shortened, but its `<ID>-n` marks and `old→new` values stay.
- date: YYMMDD (260905). Inside a decision a date appears only as measurement provenance (`measured 260903: 424 of 572`), never as who decided when.
- task st: `todo` → `doing@date.tag` → `done@date`. Stuck: `blocked@date` (one-line reason in the task's ## result). tag = 2-4 chars chosen by the claiming session
- empty value: `-` (never leave a cell blank)
- log·chg: `- YYMMDD text`, one line each, newest on top
- flow: A → B(x|y) → C — order and branches
- commands (verify etc.): backtick code, runnable as-is, no inline commentary

## Skeletons (section order fixed; only (opt) may be omitted; no sections beyond the skeleton)
- ssot: `# <ID> <name>` / `> rN | <one-line purpose>` / `## decisions` / `## flow`(opt) / `## constraints`(opt) / `## chg`
- task: `# T### <title>` / `> st:.. | ssot:<decision IDs, space-separated> | base:<ID>@rev(per referenced domain, space-separated) | dep:T### or - | touches:<repo-relative paths or ->(opt) | lane:<kebab-case or ->(opt) | explore:<N>m or <N>h or ->(opt)` / `## goal` / `## acceptance` / `## impl notes` / `## result`(filled at done·blocked — empty means untouched)
- task result lines: `- outcome: <what works now>` / `- at: <git commit SHA the checks ran on, or ->` / `- verified: <the checks that actually ran>` / `- limits: <what is still open, or ->`. Anything a later change must obey is not a result — raise it to the SSOT.
- ideation: `# IDEATION <slug>` / `> st:.. | <one-line want>` / `## vision` / `## explored` / `## shape` / `## domains` / `## open` — file ideation/<slug>.md, slug=kebab-case
- review: `# REVIEW <slug>` / `> st:.. | scope:<paths or all> | at:<git sha7 or -> | base:ARCH@rev` / `## summary` / `## findings` / `## notes` — file review/<slug>.md, slug=kebab-case (recommended `<scope>-<YYMMDD>`)
- report: `# REPORT <YYMMDD>-<tag>` / `> mode:autopilot | host:<name> | from:<ISO> | to:<ISO or -> | push:<branch or ->` / `## done` / `## decided` / `## parked` / `## checks` / `## next` — file reports/<YYMMDD>-<tag>.md
- STATE: `## cfg` / `## active`(opt) / `## inbox`(opt) / `## ideation`(opt) / `## ssot` / `## review`(opt) / `## tasks` / `## work`(opt, work-group checkpoint) / `## next` / `## log`

## Reading
- Read by purpose: the rule in force → that SSOT's decisions·flow·constraints · what changed → that SSOT's chg, only the rev range you need · how something was built and verified → the one tasks/done/ file you are investigating.
- Task context comes from `vibe brief <T###>` (a work-group worker gets the same brief from its runner): the task; the current rules of each cited domain (cfg brief `domain`) or only the cited decisions (`cited`); every decision they require or delegate to; decisions that reference a cited one; the global rules (cfg always); the flow·constraints of each domain it draws from; the chg lines after a stale base — all from one source, the working tree or one commit (`--ref`). Planning asks for `<ID>-n` (with who references it), `<ID>` or `<ID>@rev` (the chg lines after rev and the decisions they changed). Open an original only for what the brief reports missing, unfollowed or related that the work needs.
- Completeness is per block: a decision block runs to the next top-level bullet or heading, and a doc without its last section (ssot `## chg`, task `## result`) has an unbounded last block. A brief is whole only when its last line `end … chars:N` is visible and it says complete:yes. A cut-off read or brief is re-read before anything is judged.
- Read one doc per call; read a large doc section by section. Editing a doc (planning, doc-review) means reading that doc whole.
- tasks/done/ is an archive of history: never read it in bulk, and never as a source of current rules (its st·base·ssot are as of completion). Open it to investigate a named task, the change behind a regression, or what was verified before. Listing filenames (numbering, dep satisfaction) is not reading them.
- reports/ is history too: open only the reports whose inbox lines are still unresolved, newest first.

## State rules
- STATE cfg `brief`: the scope of a task brief. `domain` (absent ⇒ domain): every current decision of each cited domain, whole. `cited`: only the cited decisions and what they reference — switch to it only when tasks cite every decision their implementation must obey.
- STATE cfg `always`: the global rules every task brief carries — decision IDs or whole domains, space-separated (`ARCH-1 ARCH-4 SEC`); `-` = none; absent ⇒ every ARCH decision. Keep it to rules every task must follow (conventions, test policy, verify tiers) and decide membership when an ARCH decision is added.
- STATE cfg `push`: the branch every finished unit is pushed to (`main`, `work/x`); `-` = commit only; `?` = not chosen yet (start-vibe asks once).
- STATE active row `tag|host|mode|since|at|doing`: one row per running session. mode = pair|autopilot, since·at = ISO UTC, at = when this row was last pushed, doing = `T###` or `-`. The row is pushed before the session's first change and removed at its end. A session is stale when the newer of at and its `wip/<tag>` branch is older than 90 minutes.
- STATE inbox: autopilot appends; a pair session shows it first. Confirm → delete the line and log it. Change → update-ssot, then delete the line. Inbox lines never move into ssot/.
- STATE ssot row `id|rev|tasked|pending|[?]`: rev=current, tasked=rev consumed into tasks, pending=unconsumed delta summary (`AUTH-5+ AUTH-2✎`), [?]=open decision count. tasked < rev ⇒ create-task target.
- tasked=0 (new domain) ⇒ pending is always `all`, meaning everything up to the current rev. Later changes are absorbed into `all`.
- STATE tasks row's ssot cell holds domains only (`ARCH BM`) — decision IDs live in the task file's quote line.
- Task touches (optional): space-separated repository-relative file/directory paths or `-`. No glob, absolute path, backslash, `.` or `..` components. Overlapping prefixes serialize work-group assignment until integration/release. Omission means unknown, not proven disjoint.
- Task dep uses space-separated task IDs or `-`. No self-dependencies or cycles. Keep task-file dep and STATE dep equal; do not introduce a second dependency field.
- Task lane (optional, work groups): kebab-case name, at most 40 chars, or `-`. Active tasks sharing a lane form one work unit; a lane-less task is a unit of its own. A unit is claimed whole, implemented in dep-then-ID order in one workspace, reviewed and integrated once. Deps inside a unit never wait for integration; a unit starts only when every dep outside it is done.
  - units must not wait on each other: a dep cycle between units (lane b → lane c → lane b) is an error even without a task cycle
  - a dep on another lane's task delays the whole dependent lane until that lane is integrated — shared prerequisites belong in a foundation unit, consumers of several lanes in a convergence unit
  - lanes keep touches disjoint; overlapping lanes are serialized
  - STATE has no lane column; never add a task to a lane already in flight
- explore tasks: the timebox is wall-clock. When it runs out, the exit line decides — record the measurements in result and finish (pair asks once first). Work groups never assign them: they and the tasks that depend on them run in the main session.
- doing·done tasks are immutable. Exception: the implementing session updating its own task's st·checks·result. Content changes become a new task.
- STATE tasks table holds remaining work only (todo·doing·blocked). At done: set st `done@date` in the file, move it to tasks/done/, delete the STATE row, leave one log line. A dep absent from the table is satisfied iff tasks/done/ holds that task's file.
- STATE work row `id|workers|total|done|remaining|running|review|blocked|updated|history` is an optional CLI-generated checkpoint. history links to `work/<group>.json`; updated is its UTC snapshot timestamp. Detailed work history is retained there rather than in the bounded STATE log. Live assignment still comes from the same-clone runtime, never this table.
- Planning changes go only through update-ssot(rev+1) → STATE pending → create-task. Never edit tasks directly.
- doc-review touches ssot/ wording only: no rev, no chg, no pending, no task — so editing never invents work. Anything that changes a condition, number, negation, obligation or scope is a planning change and belongs to update-ssot; anything ambiguous stays as written and is reported.
- ideation st: `open@date` → `ready@date` → `converted@date` (in the quote line + STATE ideation row `id|st`). Explored items reuse [o]/[x]/[?]. A domains line converted into a SSOT gets `→<ID>`; the doc becomes converted when every [o] domain has one.
- review st: `open@date` → `ready@date` → `converted@date` (in the quote line + STATE review row `id|st`). Findings start as [?]; the user adopts [o] / rejects [x] ← reason. A [o] finding turned into a task gets `→T###`; the doc becomes converted when every [o] finding has one (no [o] at all ⇒ converted at once).
- review-sourced tasks: ssot = the ARCH decisions the change enforces, `-` if none; base = ARCH@rev always; first impl-notes line `- from review/<slug> Fn`; acceptance keeps behavior unchanged (existing tests still pass). They never move ssot rev/tasked/pending.
- STATE next: 1-3 lines for human/planning resumption. Standalone/planning skills update it on exit; work-group worker/reviewer assignments live in runtime queues instead.
- Lightweight fix: bug, wording or style only; no new decision, SSOT rule, contract, storage format or migration change; at most 3 code/test files and 100 added+deleted lines (STATE excluded). No task file or rev: affected tests + fast checks, one commit with STATE log `- YYMMDD fix <area>: <what>`, then batch push. Escalate to create-task/update-ssot as soon as any condition fails.
- STATE log: delete beyond 20 lines — detailed history lives in each SSOT's chg and in task files.
- report: every autopilot run writes one from its start and updates it at push boundaries; all fresh unit sessions in one vibe loop share its tag and report. done = tasks, revs and commits · decided = the inbox decided lines with their reasoning · parked = the inbox parked lines · checks = commands and CI runs with results · next = what to do on return.

## Sessions
- `vibe loop` owns preflight once, active/report lifecycle, batching, headless fresh sessions, CI wait and stop cleanup. Unit mode (`HAERAM_VIBE_UNIT=1` or start-vibe autopilot unit1) finishes exactly one task, one planning slice (SSOT + create-task together), inbox cleanup or lightweight fix. It returns one JSON result: `{kind,id,outcome,pushed,next}`. No implementation subagents. Pair mode stays interactive and recommends a fresh conversation after each unit.
- CI waits once per pushed batch using `vibe ci wait`: gh, token API, then public HTML without unauthenticated API polling; paths-filtered/no-run pushes terminate skipped within a bound. Claude waits for shell background completion, Codex uses one blocking tool call. Never model sleep/query/report loops, including long e2e/benchmark commands. CI failures become fix tasks.
- Solo (no other live session/device): task commits remain separate, claims join the first work commit, beat runs at session start/end only. Push and report at a batch boundary: 3 tasks by default, a planning slice's tasks exhausted, session end or loop stop. A loop unit ending is not a batch boundary. Strict concurrency retains a separate claim commit/push and remote ownership check before work, then pushes each unit. Work longer than an hour is snapshotted at least hourly with `vibe checkpoint` to `wip/<tag>` — a branch of its own, never the push branch.
- Claim across clones when another session is visible: commit the doing tag and the active row and push them before starting. A rejected push means fetch, merge and check the claim again — the remote decides.
- STATE merges by section: log and inbox lines are unioned, tasks·active·work·ssot rows merge by ID, and two different edits of one row stop the merge for a person or agent to resolve.

## Workspace scope
- STATE, SSOT revisions, task states and done archives describe the current checkout. They are not shared live state across worktrees; writing and re-reading a doing tag is not an atomic claim.
- `work status` discovers standalone, planning and worker contexts. Work groups are optional and require no external orchestrator. `--workspace auto` adopts a free linked worktree when appropriate and creates an isolated worktree otherwise; `current` and `new` override that choice. A branch name is never proof of ownership.
- Each work group has one planning/target branch and checkout. Planning, SSOT edits, task numbering and STATE edits happen there with one writer. Commit the plan before assigning workers. Independent branches cannot safely allocate task IDs using their local maximum alone.
- `work claim-next` selects and reserves in one transaction: ready units (a lane, or one lane-less task) with most remaining outside descendants first, then oldest task ID. Correction work has priority, worker/reviewer slots are bounded (defaults 4/1), and pending submissions pause new assignments at max-pending (default 8). A board read or STATE next never assigns work.
- `work claim` atomically reserves a task and workspace in a versioned runtime under the common Git directory. All linked worktrees of the same clone share it. A new attempt gets a unique ID; retries do not reuse ownership from released attempts. Runtime JSON is CLI-owned, not directly edited or cherry-picked.
- Group workers keep the task's quote line and contract unchanged, update only their own acceptance checks/result and code, and record doing/blocked through `work update`. Task files remain todo until integration; runtime is authoritative for execution status. Planning changes must be handed back to the planning checkout.
- Standalone verification always has task (affected tests + fast type/lint/format checks), batch (full suite once before a code push), CI (after code push), even without explicit ARCH tiers. ARCH writes labelled `task`, `batch`, `CI` sub-lines with runnable backtick commands after a colon; conditional checks stay in separate guidance lines. A standalone `vibe check` receives HAERAM_TIER and HAERAM_DIFF_BASE (task-start commit).
- Work-group verification has three local tiers. Task: the worker runs the tests the task adds or modifies plus plausibly affected ones; `work submit` optionally re-runs explicit fast commands on the clean committed HEAD. Unit: `work integrate --verify` runs the full checks once per unit on the merged candidate. Group: `work finish --verify` runs the final gate once after every unit is integrated and records the verified commit; later commits that only save progress keep it current.
- `work start`/`work configure` store the tier commands (`--task-verify`, `--verify`, `--group-verify`) on the group; submit, integrate, finish, run and the session loop use them unless `--verify` overrides. Every check receives `HAERAM_TIER`, `HAERAM_DIFF_BASE` (task: previous lane step or unit start; unit: target before the merge; group: group start), `HAERAM_TASK` and `HAERAM_TASKS`, so a stored command can select only affected tests and the host still runs them.
- In a lane, `work submit` records a step (task, commit, checks) for every task from the current one through the last of the unbroken run of completed tasks; one submit after the last task covers the whole lane. If tasks remain, the attempt stays doing with the next taskId in the same workspace. A submit that covers the final task records ready (review pending), which does not satisfy dependencies. `work review-claim` reserves a submission in a detached review checkout; `review-finish` records approved or changes_requested with findings. Resume corrections before new work. Approval pins the submission commit; worker changes require resubmission, and a target move that overlaps the submission requires re-review. `work integrate` requires approval and merges into a separate candidate checkout, archives every task of the unit with done status, updates STATE, commits and verifies the candidate, then fast-forwards the clean group checkout if its base is unchanged. Only integration satisfies group dependencies. Main/remote integration is a separate project workflow.
- Verification records identify the exact checked commit. The archived result at/verified fields preserve each task's step evidence (host task checks, otherwise the worker's own line) followed by `integration "<command>"`; the candidate commit and integration checks are recorded in the local runtime. Integration and runner shutdown also save STATE work summaries and portable `spec/work/<group>.json` history. A candidate snapshot describes its post-integration state; that integration's resulting SHA and check timestamps are available at the next checkpoint. Fresh clones retain these Git checkpoints but do not inherit live execution ownership.
- `context` reports Git and work bindings. Plain `board` is a checkout-only file view; dependencyReady does not check ownership or policy freshness. `work board` reads one fixed group commit and overlays runtime attempts. Its claimable flag is advisory; only claim establishes ownership. Worker policy updates require explicit synchronization and verification.
- `work cleanup` removes a tool-created worker only after integration/release and ancestry/cleanliness checks, preserving ignored/untracked changes. External worktrees remain on disk; only their binding is cleared. Branches and failed candidates can remain for recovery. Release requires stopping the old worker; no automatic TTL takeover, force deletion or push is performed.
- Review records carry a unique review ID, submission ID, commit, baseCommit, owner, summary and findings. Results use verdict approved|changes_requested and findings with priority P1|P2|P3, where and message. P1/P2 findings prevent approval. Released/superseded IDs cannot approve newer submissions. Reviewers never edit code or spec in their snapshot.
- `work run` uses a built-in Codex/Claude provider or a configured command adapter with JSON input/output; it owns dispatch, heartbeat, submission and integration. Built-in workers return edits for host validation and commit (runtime status committing); command-adapter workers commit before returning. `work doctor` and `work run --dry-run` inspect configuration without model calls or claims. The runner dispatches one task at a time and hands a lane's next task to the same slot and workspace; `--task-verify`, `--verify` and `--group-verify` map to the three tiers. The runner stops on settled queues or configured dispatch/retry limits. Failed/interrupted work stays inspectable; waiting uses process events rather than repeated model calls.
- Session loop: any session or orchestrated agent repeats `work next --owner <label> --wait <s>`. It returns one action in this order — the session's own unit (`implement`/`blocked`), a correction, a review of someone else's submission, the next ready unit (`implement`) — or `wait`, `complete` (nothing left, group gate passed) or `stalled` (only a person can unblock). Waiting sleeps on the runtime without model calls. `--start` creates a group when none is active; sessions started at the same commit join the same group. `needs-reviewer` means only the caller's own submissions remain, so an independent reviewer must join.
- The loop never spends a model turn on mechanical gates: the first `next` that sees an approved unit starts its integration as a detached CLI process, and after the last integration it starts the group finish the same way. A failed background integration returns the unit to its owner as changes_requested with an `integration` finding. A dead background process is recovered with the regular proof-of-exit recover.
- Only integration, sync and finish move the group branch, so only they exclude each other; claims, submissions, reviews and corrections continue meanwhile. An approval survives a moved target when the moved files do not overlap the submission's files or any `spec/ssot/` file; otherwise it is re-reviewed. The merged candidate is still fully verified at integration. Same-clone execution is the supported scope.
- Single-provider runs use `--provider`; mixed runs use `--providers codex,claude` or an adapter workers array with per-worker models. Lists repeat over the group's configured worker slots; reviewers have a separate limit. Vacant slots claim dependency-ready tasks dynamically. Every meaningful runtime transition appends atomic history, queryable with `work history`. Heartbeats do not append history. `work sync` saves a Git checkpoint from an isolated candidate without overwriting dirty planning files; it refuses a live runner or task operation. A sync commit touches only STATE and the work history, so it keeps approvals. A stale sync reservation requires proof of process exit and `work recover --work` before retry.
- A group with `--push <branch>` lands every integrated unit on that branch at once: integration merges the remote branch into the candidate first when it moved (STATE by section), verifies, fast-forwards the group branch and pushes. A refused push is recorded and retried by the next integration or sync. One blocked unit never holds finished ones back.
- A check that passed on the same tree (and scope, for commands reading HAERAM_*) is not run again; unit and group gates run one at a time under the clone's heavy lock. A resubmission's task tier diffs from the commit it fixes.
- Review policy `risky` (default) sends a unit to review only when one reason holds: changed lines over the limit (300), files outside its touches or no touches, a configured review path, no test file changed, rework after a review or integration failure, or an inbox `decided` line naming its tasks. Other units are approved by policy and still fully verified at integration. Policy `all` reviews every unit.
- Explore tasks and every task depending on them are never assigned; when only they remain, next returns `main-session` and the group can finish without them.
- Unattended (`--autopilot`), a worker blocked by a planning decision files it (question, options, recommendation) and its slot moves on. The coordinator (`next --coordinator`) answers it with a provisional update-ssot in the planning checkout, refreshes that task's base, and resumes the attempt with a note; the runner merges the group branch into the workspace and continues the same agent session. Workers still never write SSOT.
- Saved group names cannot be reused by start, including in a fresh clone. Start with a new name to preserve previous history files and STATE work rows. Without local runtime, `work history` reads the saved snapshot without restoring execution ownership.
- Existing standalone documents keep the original STATE and done workflow. Installing skills does not rewrite existing FORMAT/STATE; work-group behavior is an explicit optional protocol and uses the same task-file skeleton.

## Language
- Every spec/ doc is written in English. Code, identifiers, and paths stay as-is.
- cfg.lang = the user's language: interviews, confirmations, and reports happen in it. cfg.docs = doc language (default en).
- Exceptions: spec/NARRATIVE.md (written by create-narrative) is a human-facing prose doc in the user's language — FORMAT notation does not apply to it. It is a derived view of ssot/: it never introduces decisions, and on conflict ssot/ wins. reports/*.md are written for the owner in cfg.lang; their headings, quote-line keys and IDs stay as defined here.
