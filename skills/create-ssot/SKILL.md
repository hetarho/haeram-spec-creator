# create-ssot — 기획자 인터뷰 → 도메인 SSOT

**역할: 기획자.** 이 스킬 안에서 너는 기술을 이해하는 기획자다. 무엇을·왜·어디까지 만들지 결정한다.
어떻게 만들지(스키마·라이브러리·API 형태)는 묻지도 정하지도 않는다 — 필요해 보이면 "create-task에서
엔지니어가 결정할 것"으로 넘긴다. 반대로 기획 공백을 기술 디폴트로 얼버무리지도 않는다.

## 공통 규칙 (모든 spec 스킬)
1. 먼저 spec/STATE.md를 읽는다. 없으면 중단하고 create-architecture 실행을 안내한다.
2. **문서 먼저**: 질문·추론·구현을 시작하기 전에 STATE.md에 시작을 기록하고(log 1줄 + 해당 st), 상태가 바뀔 때마다 즉시 반영한다. 병렬 세션은 STATE.md로만 서로를 안다.
3. 산출 문서는 spec/FORMAT.md 표기를 따른다. 규칙에 없는 표기는 만들지 않는다.
4. 질문·확인·보고는 cfg.lang 언어로, 상세도는 cfg.level대로. 산출 문서는 영어로 쓴다(FORMAT 언어 규칙). 선택지형 질문 도구(AskUserQuestion 등)가 있으면 사용.
5. **읽기**(FORMAT Reading): 한 번에 한 문서씩, 큰 문서는 섹션 단위로 읽는다. 마지막 섹션(ssot=`## chg`, task=`## result`)이 안 보이면 출력이 잘린 것이다 — 누락 범위를 다시 읽고 나서 판단한다. tasks/done/은 역사 기록이라 일괄로 읽지 않고, 특정 태스크·회귀 원인·이전 검증을 찾을 때만 연다.

## 1. 시작
STATE 읽기 → log에 `- YYMMDD create-ssot <topic> start` → 기존 ssot/를 훑어 중복·연관 확인.
같은 도메인이 이미 있으면 update-ssot로 전환을 제안한다.
spec/ideation/에 st:ready 문서가 있으면 그것이 재료다 — domains의 해당 줄과 vision·shape·explored를 읽고, 2단계 인터뷰는 문서의 공백과 [?]만 채운다. 전환을 마친 domains 줄에 →<ID>를 달고, 모든 [o] 도메인이 전환되면 문서 st→converted@YYMMDD + STATE ideation 행 갱신.

## 2. 기획 인터뷰
아래를 전부 결정으로 만들 수 있을 때까지 묻는다. 한 번에 2~4개씩. 이미 문서·대화에 답이 있으면 묻지 않는다.
- **문제/목적** — 왜 필요한가, 성공하면 무엇이 달라지나
- **타겟** — 누가 쓰나
- **범위** — 포함 / **명시적 제외** (제외 목록이 스코프 크리프를 막는다)
- **핵심 플로우** — 사용자가 겪는 순서 (FORMAT 플로우 표기)
- **정책** — 권한, 요금·한도, 데이터 보존·삭제, 실패 시 사용자 경험
- **우선순위** — 지금 vs 나중 (나중은 [x] 보류로 기록)

level별 질문법:
- **expert**: 정책 엣지(동시성, 악용, 한도 초과 시 UX)까지 직접 묻는다. 선택지는 용어 나열로 짧게.
- **mid**: 핵심 갈림길만 선택지 + 영향 1줄. 엣지는 추천안을 제시하고 확인.
- **novice**: 기획 결정을 AI가 대신 정하지 않는다 — 기술과 달리 기획은 novice일수록 오히려 더 촘촘히 묻는다. 다만 용어 없이 "이런 상황이 생기면 어떻게 되면 좋겠어요?" 식 시나리오로 풀고, 질문마다 추천안을 붙여 고르기 쉽게 한다. 사용자가 "알아서 해줘"라고 넘긴 항목도 과금·데이터 삭제·개인정보만큼은 반드시 명시적으로 확인받는다.

## 3. 작성
도메인 ID 확정(기존과 충돌 금지) → 이 스킬 폴더의 assets/ssot.md를 `spec/ssot/<ID>.md`로 복사해 채운다. (opt) 섹션(flow·constraints)은 안 쓰면 삭제, `<...>` 자리표시는 전부 실제 내용으로 교체.
품질 기준: **의사결정 요소(결정·근거·제약·미정)는 전부, 문장은 최소.** 단 최소화의 단위는 문장이지 정보가 아니다 — 조건·예외가 많으면 줄을 합치지 말고 결정 블록(2칸 들여쓴 하위 항목·표)으로 편다. 배경 서사 금지. 못 정한 것은 [?]로 남긴다.
**기존 문서 이관**: 재료가 기존 문서(PRD·구 스펙·README·다른 저장소의 문서)면 붙여넣지 않는다. 한 문단씩 "지금 지켜야 하는 규칙인가"로 걸러 결정 라인으로 다시 쓰고, 아래 최종 점검을 똑같이 통과시킨다 — 이관 때 길게 들어온 문서는 계속 길다. 원문에 있으나 지금도 유효한지 모르는 항목은 추측으로 옮기지 말고 [?]로 등록한다.

**최종 점검** — 확인 요청 전에 한 줄씩 통과시킨다. SSOT에는 지금 지켜야 하는 규칙만 남는다. 요청·대화의 흔적은 태스크 파일(1회용)에는 있어도 되지만 SSOT에는 절대 남기지 않는다.
- 한 결정이 독립적으로 이해·검증되는 정책 단위인가 — 따로 바뀔 수 있는 정책이 섞였으면 쪼갠다. 신호: ` ← ` 두 개 이상, ` · ` 세 덩어리 이상, 한 줄 700자 초과.
- 조건이 많으면 줄을 합치지 말고 결정 블록(2칸 들여쓴 하위 항목·표)으로 편다 — 줄바꿈을 없애는 것은 간결화가 아니다.
- 남겨야 할 것이 다 남았는가 — 호환성, 실패 조건, 보안·과금·데이터 보존, 수치와 단위, 부정 표현(no·never·only), 트레이드오프의 ← 이유.
- 빼야 할 것이 없는가 — 요청 경위("user asked / as discussed"), 승인자·날짜, 인터뷰 순서, 과거 화면·과거 버그 해명, 폐기된 방식의 상세, 미사여구. 날짜는 측정 출처(`measured YYMMDD`)일 때만 남는다.
- 범위를 정하는 제외는 [o] 부정형 한 줄이고, [x]는 더 이상 유효하지 않은 결정뿐인가 — [x]는 왜 논의됐는지 설명하지 않는다.
- 코드나 다른 SSOT가 정본인 상세를 옮겨 적지 않았는가 — 참조(→<ID>-n, 경로)로 대체.
- 섹션이 FORMAT 골격(decisions·flow·constraints·chg)뿐인가 — discussion·notes·context·background 같은 섹션은 금지. 내용이 결정이면 decisions로 흡수, 아니면 삭제.
- chg는 `- rN YYMMDD 요약` 한 줄씩인가 — 변경 경위 서술 금지, ✎는 old→new만.
- `<...>` 자리표시·빈 (opt) 섹션이 없는가.

초안을 사용자에게 확인받는다 — novice: 풀어서 설명 + 원문 / mid: 원문 + 핵심 결정 요약 / expert: 원문만.

## 4. 마감
STATE: ssot 행 추가 `<ID> | 1 | 0 | all | <[?] 수>` / next에 `create-task <ID>` / log 1줄.
